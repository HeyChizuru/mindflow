# 阶段三：后端适配

依据 [spec](./spec.md)、[plan 阶段三](./plan.md#阶段三后端适配)、[源码盘点](./源码盘点.md) 和 [阶段二交付记录](./tasks-范围清理.md#交付记录)，展开已对齐的七项后端功能：完整课堂读取、播放位置保存与恢复、逐题提交与选择题判分、简答批改、主动重做、幂等与并发、失败恢复。

本文件为实施任务文档。单次请求完成简答保存与批改、服务端处理时限和手动恢复方向已由用户确认；具体恢复规则见下文。B1～B6 的契约、持久化及后端业务实现已交付；随后按用户“按照顺序，完成 task 上的后续所有步骤”要求完成 B7 的真实 HTTP、第三方模型、完整执行期限、进程中断恢复与存储失败验证。本 task 的后端步骤和完成标准均已完成，证据与环境边界见最后的交付记录。spec 的 draft 状态保持不变，不将后端 task 完成扩大为 CP-1～13 的整个功能验收。

## 目标与边界

以 PostgreSQL 为唯一持久化事实来源，完成“读取课堂 → 保存位置 → 逐题提交 → 判分或批改 → 再次读取恢复”的后端闭环。

- 只有答案、位置或批改结果实际保存成功，才返回对应的保存成功；答案已保存不等于批改完成。
- 持有课堂 id 即可访问，同一课堂共用一套记录，不按昵称建立独立档案。
- 只恢复最近一次成功保存的提交及状态、结果；不提供历史尝试列表、整课总分或学习统计。
- 本阶段不改课堂页面、store、播放引擎或测验组件。自动开播、字幕、下一段、重播、临时输入保留及页面状态留阶段四／五。
- 不生成或修改大纲、场景、讲稿，不调度后台续生成，不实现真实讨论、登录、Worker 或独立队列。

## 接口与状态方案（供审阅）

### 请求职责

- `GET /api/classroom?id=…`：读取课堂、定稿目录、已保存完整场景、位置和各题当前记录。保留现有入口所需的课堂基础字段，新增就绪、恢复位置与答题状态契约；草稿、首场未就绪等使用明确的业务分支。前端解析适配留阶段五，不以兼容当前临时解析器代替正式契约。
- `PATCH /api/classroom?id=…`：提交目标 `sceneId`，校验后保存位置，只更新播放位置。
- `POST /api/quiz-grade`：统一逐题提交与判分。新提交携带课堂、场景、题目、答案、本轮请求标识和所基于的记录版本；选择题在同一次事务中保存答案与判分结果，简答在一次请求内依次完成答案保存、取得批改执行权、模型批改和结果保存。题干、满分、解析和评分依据从库中读取；只在确需发起模型调用时解析本次对话配置。原答案批改重试也使用此接口，显式引用当前提交与本轮批改请求标识，不把重试当作重做。
- 当前记录及冲突后的最新记录由完整课堂读取和提交／批改响应提供，不另增历史列表、重做开始或取消接口。

**已确认：简答保存与批改由一个接口、一次请求完成。** 前端不再串联“保存答案”和“请求批改”两次请求；服务端仍须在调用模型前保存答案，在结果落库后才返回批改成功，中途失败通过响应和后续读取区分答案是否已保存。普通读取只恢复记录，不自动启动模型；失败后由用户通过同一提交接口显式重试。

### 数据与状态

- 每个场景内每道题保留一条当前记录，题目 ID 沿用场景内字符串，不要求全局唯一或改成 UUID。记录关联课堂和场景，并在课堂／场景删除时级联清理。
- 当前记录保存答案、提交标识、记录版本、批改状态、对应结果及必要时间；批改执行还保存执行标识、开始时间和到期时间。新提交成功时替换当前提交身份，旧得分不能留作新答案结果。不为此建立面向用户的历史尝试库。
- 无记录表示未提交；已存简答区分待批改、批改中、批改失败、批改完成；选择题保存成功即有最终结果。待批改、批改中、失败状态没有本次最终得分，不能用零分填充。
- 提交标识识别同一轮答案请求，记录版本识别提交所依据的旧记录；批改请求标识识别同一轮批改，执行标识隔离实际执行者。标识随该轮重试复用，不能每次重发都产生新轮次。
- 对重复请求先核对提交身份与答案是否一致；同一标识携带不同内容须拒绝，不能覆盖原记录。旧轮次重发遇到新版本时返回冲突，不把它当作新重做。

B1 已落地的具体契约：`operation: submit` 携带 `requestId / expectedVersion / answer`，首次的 `expectedVersion` 必须显式为 null，成功保存以该 `requestId` 作为提交身份；答案按 `single.value / multiple.values / short_answer.text` 区分。`operation: retry` 携带当前 `submissionId`、新的 `requestId` 及所观察的 `expectedExecutionId`（尚无执行时为 null）；取得新执行权时同时比较这个旧执行身份，避免更早轮次的重试在后续失败后又启动一次批改。四种保存状态为 `pending / processing / failed / completed`，非完成状态不带本次得分。

错误响应中的 `answerSaved` 表示本请求对应提交是否已保存，无法确认时为 null；`submissionId` 表示本请求对应的提交身份。`record` 可携带当前库内记录，因此竞争失败时允许返回 `answerSaved: false` 和胜出页面的记录，不把胜出答案当成本次答案保存成功。

### 批改时限与中断恢复

按用户确认的方向采用以下实施规则，不新增后台任务系统：

- **单次执行时限为 120 秒。** 在 `lib/services/quiz.ts` 集中定义时限常量，从数据库原子取得批改执行权时起算，保存该次执行标识、开始与到期时间；到期判断及结果写回条件以数据库时间为准。模型调用和结果写回均受该期限约束，不能只设置浏览器等待时间。
- **正常失败立即结束。** 模型调用失败或输出无效时，立即按当前提交和执行身份条件写入批改失败，保留答案，不等 120 秒。数据库写入失败则如实返回存储错误，后续通过读取和到期恢复处理，不假称失败状态已经保存。
- **到期即失去写回资格。** 正在运行的请求到期时尝试取消上游调用，并条件记录超时失败；取消不保证第三方立即停止。超过期限的执行即使晚返回，也不能保存成功结果或覆盖新执行；不能只依赖进程内计时器判断有效性。
- **刷新与普通读取不发起批改。** 未到期且仍在处理时返回处理中；已到期但尚未收敛的记录返回执行已过期的可恢复信息，页面可提示超时并提供重试／重做入口。GET 不写状态、不申请执行权，不因刷新或客户端断开自动重试；已完成记录始终直接恢复结果。
- **通过同一个 POST 收敛并恢复。** 用户明确重试或重做时，先根据当前提交、执行标识和数据库到期时间条件地将过期执行收敛为失败，再继续处理本次操作；若并发请求已完成或替换该记录，重新读回最新状态，不无条件覆盖。服务重启后也走此路径，无需依赖旧请求执行清理。
- **重试与重做分开处理。** 失败或过期后可重试原答案，也可主动重做；未到期的批改中仍禁止改答和重做。重试保留当前答案和提交身份，以新的批改请求标识开启一次新执行；同一轮网络重发复用原标识，不成为第二次执行。已保存但尚未取得执行权的待批改答案也允许显式重试。
- **不自动重新调用模型。** 不因超时、刷新、读取、存储异常或恢复服务而自动发起下一次模型批改；新调用必须来自用户明确提交或重试。结果保存响应不确定时先读库，已有最终结果直接返回。确实未保存且原执行结果已丢失时，保留答案并由用户选择是否重新批改。
- **明确外部调用边界。** 数据库条件更新负责防重复执行与拒绝旧结果；超时后的新执行须先使旧执行失效，再按新身份取得执行权。第三方是否已执行有时无法确认，用户显式重试仍可能再次产生外部模型调用；不承诺第三方调用绝对一次，不用永久锁住记录代替恢复能力。

- [x] 同一轮重复提交返回当前已存结果／状态；并发首次提交通过唯一约束决出胜者，重做通过预期版本条件替换，冲突返回可恢复的最新记录。不得使用先读再无条件覆盖。

### B5 — 简答批改、幂等与旧结果隔离
